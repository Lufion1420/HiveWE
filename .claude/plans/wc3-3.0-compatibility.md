### w3i v39 layout
VERIFIED-FILE: War3Net order reaches exact EOF on 191 of 191 once the HUD gate below is applied. Additions to v33, in order:
1. After loading_screen_number (u32): race_hud u32. Observed 1, 2, 4, 8, 64, 128. War3Net PlayerRaceHud: Human 1, Orc 2, NightElf 4, Undead 8, Selectable 64, Forsaken 128.
2. After fog_color (4 bytes), BEFORE weather_id: fog_height_start f32, fog_height_end f32, fog_linear_start f32, fog_linear_end f32, fog_max_opacity f32, fog_draw_over_sky i32. Typical (0, 0, 10000, 10000, 1, 0).
3. After min_cam_distance: hd_water_min_opacity, max_opacity, reflectivity, emissivity, edge_softness, waves_vertex_displacement, waves_normal_map_strength (each i32), hd_water_override_color (BGRA), hd_water_envmap_reflectivity (i32), alpha_tile_minimap_color (BGRA). Names per War3Net (DOCS); total size verified.
4. Player record: id, controller, race, hud_skin u32, flags, name, start xy, 4 priority masks.

TRAP, VERIFIED-FILE: the player hud_skin field is not in all v39 files. 130 stock v39 maps (editor 6117, 6127) have NO player HUD field; 61 maps (editor 6140, 7000, 7003) have it. Rule that fits all 191: player HUD present when editor_version >= 6140. 4 maps prove it from one side (prologue01, orcx01, orcx01_02, orcx02 parse only without it), 61 from the other. The other 126 parse both ways by accident: a TRIGSTR name tolerates a 4-byte shift and then reads as "STR_012". A round-trip test on names catches this; an EOF test does not. Neither War3Net nor upstream HiveWE gates this: both always read it at v39. Files from a real 3.0 World Editor should be 7000+, so most users would not hit it, but copies of stock maps would.

Weather order, VERIFIED-FILE: 6 maps have a real weather id (RLlr, RLhr, FDbh) at +24 after fog_color, confirming War3Net order. Upstream HiveWE reads weather_id first and is wrong here (its map_info.ixx near line 667).

Flags: bit 0x800000 is set in 1 stock v39 map; the HiveWE flag list stops at 0x400000 and drops it on save (map_info.ixx:412-417, VERIFIED-CODE). Meaning UNKNOWN.

HiveWE replay on v39: reaches players.resize(n) with a garbage n, for example -16777216 in 111 maps and -1 in 38 (verified replay). n is read as uint32, so about 4 billion PlayerData. INFERENCE: bad_alloc or length_error; HiveWE::load_map and main.cpp have no try/catch (VERIFIED-CODE), so an uncaught exception ends the process and any unsaved work.

### Units v12 and v13 layout
VERIFIED-FILE: exact EOF on all. Record as before plus group_id u32 after skin_id (v12+) and three 4-byte values at the end (v12+). All 33813 records are 0,0,0. War3Net calls them Unk4, Unk5, Unk6 (fixed size). Upstream HiveWE reads them as roll, pitch, light_count + lights (variable size). UNKNOWN which is right; both fit all stock data. Implementation should refuse or preserve when the third value is non-zero, not guess.
A fresh 3.0.1 save (2026-11-08) writes units subversion 9. The fresh save's trailing values are 0, 0, 0, which does not settle what the trailer is.
VERIFIED-FILE: war3mapUnits.doo subversion is 11 exactly when w3i flag 0x4000 is set, on 466 of 466 stock maps (355 set, 111 unset), rerun independently. Two 3.0.1 World Editor saves have it unset and are sub 9. INFERENCE: the editor reads this flag. File extension and game_data_version do not decide it.
VERIFIED-FILE: on sub 9, hero str, agi, int and the item table link are absent from the units file. A 3.0.1 save with Str 1, Agi 55, Int 77 holds them only in war3map.j (SetHeroStr, SetHeroAgi, SetHeroInt, ItemTable000000_DropItems). User check, 2026-11-08: reopening that map in the 3.0.1 World Editor reset the attributes and the default-stats checkbox, also after re-saving. The item table was not reported. hp is a percent there (hp 50, script `0.50 * life`), mp is absolute.
VERIFIED-FILE: group_id is 0xFFFFFFFF on an ordinary unit, a hero and a start location in that save, and on all 33813 stock records. A fresh start location's random payload is 01000000.

## 4. MDX

VERIFIED-FILE, all 15089 MDLX stock models: v1800 15087, v1700 1, v1600 1. HiveWE LATEST_MDX_VERSION = 1200 (mdx.ixx:669). Chunk structure still walks cleanly. New tag DILG in 3 sampled models; HiveWE skips unknown tags (mdx_reader.cpp:814), no issue.

GEOS SKIN, BREAKS. SKIN count is elements of u16 at v1800. Boundary v1400 per upstream (DOCS). HiveWE reads u8 (read_GEOS, read_vector of uint8_t), then desyncs. VERIFIED-FILE by exact inclusive-size match: with 2-byte elements every tested file passes; with HiveWE 1-byte:
- base layer, all 3225 v1800 files: 112 fail (98 doodads, 8 cinematics, 2 objects, 2 ui, 2 units), for example cityscape citywall, orgrimmar gate.
- _hd sample (415 files, 1 in 12): 414 fail. _de sample (439): 436 fail.
Effect per code: exceptions are caught by ResourceManager, which returns an error; doodad and unit get_mesh fall back to Objects/Invalidmodel (doodads.ixx:521, units.ixx:536; VERIFIED-CODE). INFERENCE: placeholder model, unless garbage counts happen not to throw, giving bad geometry. With hd True nearly every model fails. With hd False (current setting) about 3.5 percent, mostly structural doodads.
Writer: to_mdx writes u8 skin; Map Protector rewrites imports with model.to_mdx(model.version) (asset_obfuscation.ixx:887), so a reader-only fix would corrupt v1400+ imports. Fix both.

LITE, misread, non-fatal. HiveWE v1200 layout on v1800 leaves 24 extra bytes in 576 of 582 lights (VERIFIED-FILE). Per upstream (DOCS for names and boundaries; total 24 verified): v1300 inserts shadow_casting u32 BEFORE attenuation_start, plus shadow_casting_start and shadow_casting_end f32 after shadow_intensity; v1600 adds quadratic_falloff, linear_falloff, damping f32. So attenuation, colour and intensity read shifted by 4 bytes, with 6 unknown-tag prints per light. No desync since the loop uses inclusive size. Upstream also reads KLAS and KLAE as float tracks where HiveWE uses uint32 (not verified).

MTLS: 2205 of 2205 pass in a 900-file sample with the existing post-v1100 layer walk (VERIFIED-FILE). Other chunks not byte-checked.
